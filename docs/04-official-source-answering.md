# 04. 공식 원문 조회 기반 답변 설계

> 2026-10-22 갱신. 법령·고양시 조례의 공식 검색·조문 읽기 도구는 구현했고 공개 테스트 API로 확인했다. 서비스용 인증·배포 환경 접근 검증과 정책 전용 도구는 아직 남아 있다.

## 권장 방향

문서를 미리 잘라 임베딩한 뒤 비슷한 문장을 찾는 방식을 주 경로로 두지 않는다. 질문을 받은 시점에 공식 출처를 검색하고, 특정 버전의 원문을 읽고, 확인한 근거로만 답한다. 기존 에이전트에 조회 도구를 추가하면 되며 별도 에이전트 플랫폼이나 벡터 DB를 추가할 필요는 없다.

넓은 의미에서는 검색 근거를 사용해 생성하는 방식도 RAG에 속한다. 여기서 바꾸려는 것은 **사전 적재·벡터 유사도 중심 검색을 공식 원문 조회 중심으로 바꾸는 것**이다. 실시간 조회만으로 정답이 보장되지는 않는다. 적용 시점과 지역, 원문이 실제로 뒷받침하는 범위를 검증해야 한다.

## 현재 구현과 차이

| 영역 | 현재 | 권장 경로 |
| --- | --- | --- |
| 법령·조례 | 공식 API로 현행 버전 검색·조문 읽기. 본문 식별자·시행일·관할 검사. 법규를 적재 문서 벡터 검색에서 제외 | 과거 시점 버전 선택·부칙 전체·별표 검증 추가 |
| 정책 | 전용 조회 도구 없음 | 소관 기관의 공고·보도자료·사업지침 검색 → 본문과 첨부 원문 확인 |
| 회의록 | 고양시의회 검색과 발언 블록별 발췌. 본인 발언 화자 검사·회의일·임시 기록 여부 표시 | 위원회·안건·의결 상태와 발췌 범위 보강 |
| 행감 지적 | PDF 추출 DB 조회 | 구조화 DB를 탐색에 활용하고 최종 주장의 근거는 보고서 쪽수·원문으로 확인 |
| 답변 검증 | 인용 번호가 있는지 확인 | 근거 식별자·실제 발췌·날짜·지역 검사, 주장별 근거 대조, 확인 불가 분리 |

## 공식 출처 조사

- [법제처 OPEN API 활용가이드](https://open.law.go.kr/LSO/openApi/guideList.do): 현행·연혁 법령, 조항호목, 자치법규, 행정규칙, 법령해석례 등의 목록·본문 조회를 제공한다. 등록과 신청한 API 인증값이 필요하다.
- [시행일 법령 목록 API](https://open.law.go.kr/LSO/openApi/guideResult.do?htmlName=lsEfYdListGuide): `target=eflaw`, `nw`로 현행·시행예정·연혁을 구분하고 법령명·본문 검색, 시행일 범위 등을 지원한다.
- [시행일 법령 본문 API](https://open.law.go.kr/LSO/openApi/guideResult.do?htmlName=lsEfYdInfoGuide): `ID`로 현행 본문, `MST`와 `efYd`로 식별한 버전의 본문을 조회하며 `JO`로 조문을 지정할 수 있다. 단순히 오늘 날짜를 `efYd`로 넣어 과거 버전을 선택하는 설계는 하지 않는다.
- [정책브리핑](https://www.korea.kr/main.do): 정책뉴스·부처별 뉴스·보도자료·전문자료가 있다. 공식 메인에 RSS 제공 중단 안내가 있고, 기존 RSS 안내 주소는 메인으로 이동한다. RSS가 계속 제공된다고 가정하지 않는다. 서비스용 검색/API의 제공 조건은 별도 확인이 필요하다.
- [고양시의회 회의록](https://www.goyangcouncil.go.kr/promote/minutes/search.do): 회의·연도·의원별 검색을 제공한다. 기존 수집 코드를 활용하되 HTML 변경·일시 장애·공개 지연을 다룬다.
- [고양시의회 의안검색](https://www.goyangcouncil.go.kr/promote/bill.do): 발언과 실제 의안 처리 결과를 구분할 때 대조할 후보 출처다. 연동 구현과 응답 구조 검증은 아직 하지 않았다.

공공데이터포털 키가 있다는 사실만으로 법제처 DRF API 접근 권한이 생기지 않는다. 사용자에게 확인한 결과 서비스용 인증값은 아직 발급 전이다. 키 값은 조사·문서·답변에 노출하지 않는다.

## 구현한 법령 조회의 설정과 검증

- [법제처 공동활용 신청](https://open.law.go.kr/LSO/usrJoin.do)에서 받은 OC 인증값을 로컬 `.env.local`과 배포 환경에 `LAW_API_OC`로 설정한다. 이 값은 서버에서만 사용하고 `NEXT_PUBLIC_` 변수로 만들지 않는다. 실제 배포 주소의 이용 등록·접속 허용 조건은 발급 과정에서 확인한다.
- 인증이 없으면 ‘공식 조회 미설정’으로 안내한다. 적재 법령이나 모델 기억으로 최신 법령을 대신 답하지 않도록 한다.
- 도구는 질문별로 검색한 `candidateId`만 읽을 수 있다. 모델이 임의 법령 ID·URL·관할을 넣어 조회 경로를 바꾸지 못한다.
- 검색 목록에는 출처 번호를 주지 않는다. 검색 결과의 버전 번호로 본문을 읽고 법규 ID·명칭·시행일·관할을 대조한 발췌에만 번호를 붙인다. 조회 실패는 자료 없음과 구분하고, 다른 자료로 답했어도 조회하지 못한 항목을 끝에 표시한다.
- 15초 제한시간, 4MiB 응답 상한, 검색 8건·발췌 5개 상한을 둔다. 조문을 중간에서 잘라 완전한 근거처럼 쓰지 않는다. 초기 구현은 캐시 없이 조회한다.
- 공개 테스트 API로 `지방자치법` 검색 → 확인한 현행 버전의 제49조, 고양시 조례 검색 → 선택한 조례 제1조를 실제 코드로 읽었다. 공개 테스트 인증값을 앱 기본값이나 배포 설정에 저장하지 않았다.
- `npm run test:legislation`은 공식 응답 fixture로 파싱·버전·관할·오류·인증값 비노출을 검사한다. fixture는 2026-10-22 공개 테스트 응답에서 필요한 필드만 보관한 것이며 실시간 현행성 검사 자체는 아니다.
- 서비스용 인증값, 배포 환경 접근, 실제 AI가 도구를 올바르게 선택하는 전체 질의 응답 평가와 브라우저 검증은 아직 수행하지 않았다.

회의록의 `speaker-block`에서 화자 이름과 발언 본문을 나눠, 본인 발언은 이름이 일치하는 블록에서만 발췌한다. 이번 질문에서 검색한 회의록 UID만 도구로 읽을 수 있으며 회의일·임시회의록 여부를 출처에 표시한다. 실제 공개 회의록 UID 15688에서 화자 일치 발췌와 없는 화자의 빈 결과를 확인했다. 모의 응답 검사에는 다른 사람의 발언 속 이름 언급·참석자 목록·스크립트 속 가짜 발언을 포함했다. 현재 사이트의 평면 HTML 구조를 기준으로 하므로 구조 변경과 동명이인은 여전히 제약이다.

## 답변까지의 처리 순서

1. **범위 결정**: 의회·위원회·부서·사업·기준일을 정한다. 현재 법령인지 과거 사건 당시 법령인지 구분한다. 답이 달라지는 정보가 빠졌으면 사용자에게 확인하고, 가정으로 답할 때는 기준일을 명시한다.
2. **공식 후보 검색**: 법령은 법제처, 정책은 소관 부처와 고양시, 회의는 고양시의회에서 찾는다. 일반 웹 검색은 공식 원문을 발견하는 보조 수단으로만 사용한다. 검색 결과의 요약문만으로 사실을 확정하지 않는다.
3. **본문 확인**: 법령 ID·버전·조문, 정책 문서 번호·발표일·첨부, 회의 UID·발언 구간으로 원문을 읽는다. 본문을 읽지 않은 후보는 답변 근거로 등록하지 않는다.
4. **근거 묶음 구성**: 서버가 자료별 식별자를 발급하고 URL·문서 종류·기관·기준일·조회일·원문 발췌·위치 정보를 묶는다. 모델이 URL이나 인용문을 임의로 만들지 못하게 한다.
5. **초안 작성과 검증**: 사실 주장마다 근거 식별자와 원문 발췌를 연결한다. 존재하지 않는 식별자와 원문에 없는 직접 인용은 코드로 거절한다. 의미 일치와 법령 적용은 평가 세트 및 표본 검수로 확인한다. 두 번째 모델 검토를 추가해도 검증된 정답으로 취급하지 않는다.
6. **답변 표시**: 확인한 사실, 해석, 확인되지 않은 부분, 다음 확인 질문을 나눠 쓴다. 출처에는 시행일/회의일/발표일과 조회 시점을 붙인다. 출처 개수로 정확성을 점수화하지 않는다.

## 법률·정책·회의별 필수 구분

- **법률**: 법률·시행령·시행규칙·자치법규와 위임 관계를 확인한다. 공포일과 시행일, 현행과 시행예정, 사건 당시 버전, 부칙의 경과조치를 구분한다. 조문이 요구하는 요건을 사건 사실만으로 확인할 수 없으면 위법·적법을 단정하지 않는다.
- **정책**: 발표·입법예고·시행·신청 가능·종료를 구분한다. 보도자료만으로 확정된 지원 자격이나 법적 의무라고 답하지 않는다. 지역·대상·기준연도·예산·신청기간은 사업 공고와 첨부 지침에서 확인한다. 발표 당시 계획과 실제 이행 자료가 충돌하면 후속 자료를 찾는다.
- **회의**: 의원의 문제 제기, 집행부 답변, 위원회 의결과 본회의 의결을 구분한다. 특정 의원이 참석한 회의록에 단어가 있다는 것만으로 그 의원의 발언이라고 단정하지 않는다. 화자와 발언 구간을 확인한다. 반복 지적만으로 미이행이라고 단정하지 않는다.

## 최소 도구 구성 제안

기존 `runCouncilAgent`와 출처 팝오버를 재사용한다.

- 법령: `searchLegislation` → `readLegislation`. 검색은 자료 종류·키워드·시점·관할, 읽기는 검색 결과 ID와 버전·조문 번호를 받는다. 첫 구현은 현행 법령·고양시 조례로 좁히고, 과거 버전 질문에는 지원 범위를 분명히 알린다.
- 정책: `searchOfficialPolicies` → `readOfficialPolicy`. 고양시와 소관 부처 공식 게시판부터 시작한다. 제공 기관의 API가 있으면 우선 사용하고, 없으면 이용 조건과 HTML 구조를 확인한 전용 조회 코드를 둔다. 임의 사이트 전체를 읽는 범용 크롤러는 처음부터 만들지 않는다.
- 회의: 기존 `searchMinutes` → `readMinutes`에 날짜·위원회·화자 메타데이터를 보강한다. 의결 여부를 묻는 질문은 의안 처리 결과까지 확인하도록 한다.

현재 최대 6단계 제한에서 법령·정책·회의를 모두 조회하고 검증하기는 부족할 수 있다. 초기에는 질문별 필요한 출처만 선택하고, 검색 결과를 좁혀 원문을 3~5건 읽는 예산으로 측정한다. 도구 수와 최대 단계를 무작정 늘리지 않는다. 여러 출처가 필수인 복합 질문만 별도 예산을 부여하는지는 지연·비용 평가 후 정한다.

## 운영 설계

- 공식 API·사이트 주소는 서버가 정한다. 읽기 도구는 이번 요청에서 검색한 식별자만 받게 하고 임의 URL은 받지 않는다. 리디렉션 대상도 허용 출처인지 확인한다.
- 외부 문서의 지시문은 자료로 취급한다. 세션·개인 대화·API 키를 외부 검색어에 포함하지 않는다. 개인 프로필은 답변 생성에 필요한 범위로 제한한다.
- 조회 제한시간·응답 크기 제한·검색 건수 상한을 둔다. 실패는 `조회 실패`, 빈 목록은 `검색 결과 없음`, 미지원 출처는 `조회 미지원`으로 구분한다.
- 캐시 키에 문서 ID·버전·시행일을 포함한다. 현재본 검색 캐시는 짧게, 확정 버전 본문은 길게 보관한다. 오류 시 오래된 캐시를 쓰면 마지막 확인일과 최신성 미확인을 표시한다.
- DB에는 대화와 근거 스냅샷·조회 기록을 보관한다. 이 저장은 출처 재현용이며 전체 웹을 미리 벡터화하는 용도가 아니다. 기존 문서·임베딩은 새 경로를 검증하기 전 삭제하지 않는다.

## 구현 순서와 검증

1. 법제처 인증·배포 환경 접근을 확인하고 현행 법령·고양시 조례 조회부터 연결한다.
2. 회의록의 화자·날짜·발췌와 인용 식별자 검사를 강화한다.
3. 고양시 및 건설교통 분야 소관 부처의 정책 공고 본문·첨부를 연결한다.
4. 아래 유형의 실제 질문 20~30개에 원문 위치와 기준일을 사람이 붙여 평가한다. 최신 원문을 조회했는지, 사실·숫자·인용이 맞는지, 미확인을 단정하지 않았는지, 응답 시간·실패율을 본다.

| 평가 유형 | 확인할 실패 |
| --- | --- |
| 현재 법령과 시행예정 개정이 같이 검색됨 | 미래 조문을 현재 규정으로 답함 |
| 과거 감사 시점의 근거법령 | 현행 조문으로 소급 해석 |
| 같은 이름의 다른 지역 조례 | 관할을 혼동 |

| 외부 사이트 장애·본문 미확인 | 자료가 없거나 근거가 확보됐다고 잘못 안내 |
