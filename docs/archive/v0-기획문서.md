# 지방의회 의원 AI 비서 서비스 (RAG) 기획 문서

작성일: 2026-09-22
버전: v1.0 (MVP 기획 확정본)

---

## 1. 문제 정의

### 1-1. 사용자 정의
- **대상**: 전국 지방의회(광역+기초) 의원 전체
- **구조**: 멀티테넌시
  - ① 전국 공통 레이어: 법령·상위법
  - ② 의회별 레이어: 조례·회의록·안건·예산서
  - ③ 의원 개인 레이어: 본인 의정활동 이력
- **계정 체계**: 소속 의회 + 소속 상임위 + 지역구/비례 정보로 계정 초기화

### 1-2. 병목 파악
| 병목 | 내용 |
|---|---|
| 조례 제·개정 리서치 | 전국 유사조례 비교, 상위법 정합성 검토 |
| 예산·결산 심의 | 항목별 근거, 증감 사유 추적 |
| 회의 안건 분석·요약 | 상정 안건의 쟁점·배경 파악 |
| 상위 법안 조회 | 자치법규 vs 법률·시행령 정합성 |
| 의정활동 보고서 작성 | 분기/반기/연간 실적 정리 |
| 회의록·안건 이력 조회 | 과거 유사 안건/발언 추적 |

### 1-3. 대상 선정 (MVP 6개 기능, 전체 동시 출시)
① 상위 법안 조회 · ② 회의록·안건 이력 조회 · ③ 조례 제·개정 리서치 · ④ 예산·결산 심의 지원 · ⑤ 회의 안건 분석·요약 · ⑥ 의정활동 보고서 초안

> 리스크 메모: ⑥ 보고서 초안 기능은 활동 이력이 누적되기 전까지 초기 품질이 낮을 수밖에 없음. 베타 라벨 또는 초기 이력 입력 온보딩 필요.

### 1-4. 수동/자동 경계
| 업무 | AI 허용 범위 | 사람 영역 |
|---|---|---|
| 민원 대응(향후) | 검색 + 초안 작성 | 최종 발송 검토 |
| 조례 제·개정 | 검색·비교까지만 | 조문 작성·발의 판단 |
| 예산·결산 | 검색 + 이상치 하이라이트 | 심의 판단 |
| 회의 안건 분석 | 검색 + 요약 | 찬반·질의 방향 결정 |
| 상위법 조회 | 완전 자동(검색·요약) | - |
| 의정보고서 | 초안 작성 | 정치적 평가·수정 |

### 1-5. 핵심 KPI
- 환각률/근거 일치율 (조례는 초안 미제공, 검색 신뢰도가 핵심)
- 리서치 시간 단축률
- 초안 채택률 (민원 답변, 의정보고서)
- 의회별/의원별 활성 계정 비율
- 기능별 성숙도 지표 (특히 보고서 초안: 이력 데이터 축적량 대비 채택률 추이)

## 2. 업무/데이터/상태 분석

### 2-1. 업무 흐름
| 기능 | 흐름 |
|---|---|
| ① 법안 조회 | 키워드 입력 → 법령 검색 → 조문+출처 제시 |
| ② 회의록 조회 | 주제 입력 → 회의록 검색 → 시간순 목록+요약 |
| ③ 조례 리서치 | 조례 주제 입력 → 전국 유사조례 비교 → 비교표 제시 |
| ④ 예산·결산 | 사업/부서 지정 → 예산서 항목 추출 → 증감·이상치 하이라이트 |
| ⑤ 안건 분석 | 안건 등록 → 첨부자료 요약 → 쟁점 정리 |
| ⑥ 보고서 초안 | 기간 선택 → 활동이력 취합 → 초안 생성 → 검토 → 완료/보류 |

### 2-2. 데이터 정의
| 기능 | 필요 데이터 | 확보 방식(MVP) |
|---|---|---|
| ① 법안 조회 | 법률·시행령·자치법규 | 국가법령정보센터 Open API, 주간 배치 |
| ② 회의록 조회 | 본회의·상임위 회의록 | 시범의회 1곳 크롤링, **월 1회 배치** |
| ③ 조례 리서치 | 전국 자치법규 | 자치법규정보시스템 Open API, 주간 배치 |
| ④ 예산·결산 | 예산서·결산서 | 시범의회 1곳 크롤링, 월 1회 배치 |
| ⑤ 안건 분석 | 상정 안건 첨부자료 | 시범의회 1곳 크롤링, 월 1회 배치 |
| ⑥ 보고서 초안 | 개인 활동 이력 | 시스템 내부 누적(①~⑤ 이용 로그 + 수동 입력폼) |

### 2-3. 상태 정의

**문서(자료) 상태** — 모든 데이터 공통
수집됨 → 처리중 → 색인완료 / 업데이트 필요 / 오류

**요청(작업) 상태** — ⑥ 보고서 초안 기능만 적용
접수됨 → 생성중 → 초안 생성됨 → 검토중 → 완료 / 보류

**계정 상태** — 인증 체계와 연동
가입신청됨 → 승인대기 → 활성 / 거부됨 / 비활성화

①~⑤ 기능은 별도 요청 상태 없이 조회 로그만 기록.

## 3. UX/IA 설계

### 3-1. 정보 구조 (IA)
```
대시보드 (홈) — 예정·알림 중심
├─ 법령·조례 검색        ← ① + ③ (탭 구분 + 대화 목록)
├─ 회의·안건             ← ② + ⑤ (탭 구분 + 대화 목록)
├─ 예산·결산             ← ④ (대화 목록)
├─ 의정활동 보고서        ← ⑥ (대화 목록)
└─ 마이페이지
    ├─ 계정·소속 정보
    ├─ 활동이력 관리 (수동 입력)
    └─ 저장한 자료함      ← ①②③④⑤ 검색결과 북마크
```

> **대화(채팅) 이력 관리 방식(확정)**: ChatGPT처럼 메뉴당 여러 개의 대화를 생성할 수 있고, 이전 대화 목록에서 다시 불러올 수 있음. 화면마다 좌측에 "+ 새 대화" 버튼 + 대화 목록이 있는 구조. (마이페이지는 채팅형이 아니므로 해당 없음)
> → 데이터 관점에서는 "대화(conversation)" 엔티티가 신규로 필요하며, 대화 하나가 여러 메시지(질문-답변 쌍)를 포함하는 구조로 설계 (4-2 API 명세, 4-1 데이터 구조 설계 시 반영 필요)

### 3-2. 화면별 핵심 목표
| 화면 | 핵심 목표 |
|---|---|
| 대시보드 | 다가오는 안건·보고서 마감을 놓치지 않도록 안내 |
| 법령·조례 검색 | 30초 내 근거자료 확보 + 즉시 저장 |
| 회의·안건(이력조회) | 과거 유사 사례 누락 없이 검색 |
| 회의·안건(안건분석) | 상정 전 쟁점 파악 시간 단축 |
| 예산·결산 | 증감/이상치 한눈에 파악 |
| 의정활동 보고서 | 수정만 하면 되는 초안 제공 |
| 마이페이지 > 저장한 자료함 | 저장 자료 재탐색 |

### 3-3. 상태별 화면 설계 (요약)
- 검색형 화면(①②③④⑤): 빈 상태 / 로딩중 / 결과 있음(+저장 버튼) / 저장됨 / 결과 없음 / 오류
- 대시보드: 알림 있음 / 알림 없음 / 데이터 갱신 지연(최신 반영일 표시)
- 의정활동 보고서: 접수됨 → 생성중 → 초안 생성됨 → 검토중 → 완료/보류
- 저장한 자료함: 빈 상태 / 목록 있음

## 4. 시스템 구조 및 기능 명세

### 4-1. 구조 설계 (5계층)
1. 외부 데이터 소스 — 법령API · 조례API · 시범의회 크롤링
2. 수집·배치 계층 — 주간/월간 배치 + 크롤러 실행
3. 처리·색인 계층 — 텍스트 정제 + 벡터DB 색인
4. RAG 코어 — 벡터 검색 + LLM 생성
5. 서비스 계층 — 웹앱 · 인증권한 · 대시보드

### 4-2. API 명세 (개념 수준)
- 법령·조례 검색 API / 회의·안건 이력조회 API / 안건분석 API
- 예산·결산 조회 API / 자료 저장(북마크) API
- 의정보고서 생성 API / 의정보고서 상태변경 API
- 인증 API (회원가입, 로그인, 마스터 승인)

### 4-3. 배치 명세
| 배치 | 주기 |
|---|---|
| 법령 갱신 배치 | 주간 |
| 조례 갱신 배치 | 주간 |
| 시범의회 크롤링 배치(회의록·예산서·안건) | **월 1회** |
| 색인 배치 | 수집 배치 직후 실행 |

### 4-4. 인터페이스 명세
화면별 API 매핑은 위 3-1 IA 구조와 4-2 API 명세를 그대로 연결 (화면 1개당 조회 API + 저장 API가 기본 조합, ⑥만 생성+상태변경 API 조합)

### 4-5. 안정성 대비
| 항목 | 대응 방안 |
|---|---|
| 사용자/권한 관리 | **회원가입 + 마스터 계정 승인제**, 계정상태 5단계, 의회별/의원별 데이터 분리 |
| API 변경 | 응답값 검증 로직으로 스펙 변경 자동 감지 → 배치 실패 처리 + 관리자 알림 |
| 인증 만료 | 토큰 만료 시 자동 갱신 시도 → 실패 시 재로그인 유도 |
| 데이터 오류 | "오류" 상태 처리, 검색 결과 자동 제외, 재처리 큐 등록 |
| 중복 실행 | 배치 실행 중 락(lock) 처리 |
| rate limit | 외부 API 호출 간격 조절, 초과 시 다음 배치로 이월 |
| **실행 실패/정확도** | 시스템오류는 **1회 재시도**, 근거 부족 시 "답변 불가" 처리(그라운딩 검증), **모든 답변에 출처 강제 표시**, 신뢰도 낮은 답변엔 경고 표시. 법령·조례(①③)는 엄격 적용, 보고서(⑥)는 상대적으로 유연 |

## 5. UI 디자인 결정사항 (확정)

### 5-1. 프레임 목업
대시보드 기준 프레임 확정 (좌측 사이드바 + 우측 콘텐츠 영역)
- 사이드바: 로고 + 5개 메뉴(대시보드/법령·조례 검색/회의·안건/예산·결산/의정활동 보고서) + 하단 마이페이지
- 콘텐츠 영역: 데이터 최신 반영일 표시(신뢰도 안내) + 알림 카드(예정 안건, 보고서 마감) + 빠른 실행 버튼

### 5-2. UI 의사결정
| 항목 | 결정 |
|---|---|
| 네비게이션 구조 | **좌측 사이드바** (메뉴 확장에 유리, 관리자형 툴 UX와 유사) |
| 반응형 대응 | **처음부터 PC+모바일 동시 대응 설계** (별도 모바일 전용 개발 없이 반응형 1세트로 진행) |
| 데이터 신뢰도 표시 | 모든 화면 상단에 "최신 반영일" 노출 (배치 주기가 기능별로 다르므로 사용자 신뢰 확보 목적) |

### 5-3. 테마 선택
- **색상 방향(최종 지향점)**: 따뜻한 뉴트럴 계열 (그린 + 테라코타 포인트) — 공공기관의 딱딱함보다 친근하고 편안한 톤 지향
- **프레임 목업 단계**: Shadcn 기본 테마로 먼저 골격을 잡고, 이후 그린+테라코타 커스텀 컬러로 교체하는 2단계 접근

### 5-4. 프론트엔드 기술스택
| 항목 | 결정 |
|---|---|
| CSS 프레임워크 | TailwindCSS |
| UI 컴포넌트 라이브러리 | Shadcn/ui |
| 베이스 컬러 프리셋 | **Slate** (공공/관리툴 UX에 적합, 약간 푸른기 도는 회색) |
| 스타일 프리셋 | **New York** (각지고 담백한 느낌) |
| 적용 순서 | ① Shadcn 기본 테마(Slate + New York)로 프레임 목업 및 초기 컴포넌트 구축 → ② 그린+테라코타 커스텀 컬러 토큰으로 교체(테마 커스터마이징 단계) |

> 참고: Shadcn 기본 테마는 어디까지나 "1차 골격"이며, 5-3에서 정한 최종 색상 방향(그린+테라코타)은 Tailwind 설정의 CSS 변수(`--primary`, `--accent` 등)를 교체하는 방식으로 이후 적용합니다. 구조(컴포넌트, 레이아웃)와 색상(테마)을 분리해서 작업하면 Claude Code에서의 반복 수정이 더 수월합니다.

### 5-5. 인터랙션 패러다임 (프레임 목업 검수 중 확정)

**채팅 중심(LLM 느낌) 인터페이스로 확정.** 메뉴 구조는 유지하되, 각 메뉴 안에서의 상호작용은 검색결과 나열형이 아니라 채팅형 문답으로 진행합니다.

메뉴를 없애지 않고 유지한 이유:
1. **정확도(그라운딩)** — 메뉴가 질문의 데이터 범위를 먼저 좁혀줘야 AI가 엉뚱한 소스에서 검색하는 것을 방지 (법령·조례 정확도 최우선 원칙과 직결)
2. **데이터 소스가 메뉴마다 다름** — 법령API/조례API/회의록크롤링/예산서파싱이 별도 파이프라인
3. **자동화 규칙이 메뉴마다 다름** — "검색까지만" vs "초안 생성 허용"을 화면으로 명확히 구분
4. **발견성(discoverability)** — 백지 채팅창보다 메뉴+추천 소식 카드가 초심 사용자에게 유리
5. **기록·이력 관리** — 유형별로 나뉘어 있어야 나중에 재탐색이 쉬움

### 5-6. 화면별 확정 패턴

| 화면 | 확정 패턴 |
|---|---|
| 대시보드 | 채팅 입력창 + "OOO 의원님 관련 소식"을 **안건 / 회의록 2열로 구분**해 표시 + 보고서 마감 배너 |
| 법령·조례 검색 | 탭(조례/법률·시행령) + 채팅형 문답 + 결과마다 **출처 표시 + 저장(북마크) 버튼** |
| 회의·안건 | 탭(이력조회/안건분석) + 채팅형 문답 + 저장 버튼 |
| 예산·결산 | 채팅형 문답 + 증감표 + 저장 버튼 |
| 의정활동 보고서 | 채팅으로 초안 요청 → 상태배지(검토중) 노출 → **완료/보류 버튼**으로 상태 확정 (유일하게 요청상태 흐름을 화면에 노출) |
| 마이페이지 > 계정·소속 정보 | 조회 전용, 변경은 마스터 승인 필요 안내 |
| 마이페이지 > 활동이력 관리 | 자동 미수집 활동(민원 처리 등) 수동 등록/삭제 |
| 마이페이지 > 저장한 자료함 | 목록형(비채팅), 저장된 자료 유형별 배지 + 삭제 |
| 회원가입 | 이메일/비밀번호/소속의회/상임위/지역구·비례 입력 → 가입신청 → **승인대기** 화면 (계정상태 5단계와 연동) |

### 5-7. 대화(채팅) 이력 관리 — 메뉴당 다중 대화 지원

법령·조례 / 회의·안건 / 예산·결산 / 의정활동 보고서 4개 메뉴는 각각 **ChatGPT 방식의 다중 대화**를 지원합니다.
- 메뉴 진입 시 좌측에 "+ 새 대화" 버튼과 이전 대화 목록이 노출됨
- 대화를 선택하면 해당 대화의 질문-답변 히스토리를 다시 불러옴
- "+ 새 대화"를 누르면 빈 상태로 전환되어 새로운 주제로 질문 가능
- 마이페이지(계정정보/활동이력/저장자료함)는 채팅형이 아니므로 대화 이력 개념이 적용되지 않음

> 데이터 설계 영향: `conversation`(대화) 엔티티와 `message`(질문-답변) 엔티티가 메뉴별로 필요. 대화 목록 조회, 대화 생성, 메시지 추가 API가 4-2 API 명세에 추가로 필요.

## 7. 고도화 기획 (v1.1) — 실사용 MVP 보강

> v1.0은 6개 기능의 존재와 흐름은 확정했지만, "승인 없이 아무도 못 들어온다", "출처 없이 아무 답변도 못 믿는다" 같은 이 서비스의 **전제 조건을 실제로 작동시키는 화면**은 비어 있었음. 7장은 그 공백을 메우는 추가 장표·기능 기획이며, 우선순위(7-13)로 MVP 오픈 전 필수/이후 보강을 구분함.

### 7-1. 인증·계정 상세 플로우

| 단계 | 화면 | 입력/동작 | 실패 케이스 |
|---|---|---|---|
| 가입 | 회원가입 폼 | 이메일·비밀번호·소속의회·상임위·지역구/비례 | 이메일 중복, 소속의회 목록에 없음(수동 문의 안내) |
| 제출 후 | 승인대기 화면 | 안내 문구 + 예상 소요시간 | - |
| 마스터 미응답 | 승인대기 화면(재방문 시) | 대기 경과일 표시 | 장기 대기 시 문의 채널 노출 |
| 승인 | 활성 전환 | 최초 로그인 유도 알림(이메일) | - |
| 거부 | 거부 안내 화면 | 거부 사유(마스터 입력) 노출 | 재가입 신청 가능 여부 안내 |
| 비활성화 | 로그인 차단 화면 | 사유 안내 + 문의 채널 | - |
| 비밀번호 재설정 | 이메일 인증 → 재설정 폼 | 토큰 만료 시 재발급 유도 | - |
| 세션 만료 | 재로그인 유도 모달 | 작성 중이던 채팅 입력값 보존 시도 | 보존 실패 시 명시적 경고 |

> 계정상태 5단계(가입신청됨/승인대기/활성/거부됨/비활성화)는 1-3 상태 정의와 동일 값을 사용. 화면 문구만 상태별로 분기.

### 7-2. 관리자(마스터) 콘솔 — 신규 화면 그룹

기존 IA(3-1)에는 없던 별도 진입점. 일반 의원 사이드바에는 노출되지 않고, 마스터 권한 계정에만 별도 메뉴로 노출.

```
관리자 콘솔 (마스터 전용)
├─ 가입 승인 대기열   ← 승인/거부(+사유), 일괄 처리
├─ 계정 관리          ← 의회별/권한별 목록, 비활성화, 강제 로그아웃
├─ 배치 모니터링       ← 배치별 상태(성공/실패/지연), 실패 로그, 수동 재실행
└─ 오류·재처리 큐       ← "오류" 상태 문서 목록, 재처리 트리거
```

| 화면 | 핵심 기능 | 연결되는 기존 명세 |
|---|---|---|
| 가입 승인 대기열 | 승인/거부 버튼, 거부 사유 필수 입력 | 1-3 계정 상태, 3-1 마이페이지 승인 안내 |
| 계정 관리 | 의회·상임위·지역구 필터, 계정 강제 비활성화 | 1-1 멀티테넌시 구조 |
| 배치 모니터링 | 배치별 최근 실행 이력, 실패 사유, 수동 재실행 버튼 | 4-3 배치 명세, 4-5 중복실행 락 |
| 오류·재처리 큐 | "오류" 상태 문서 목록, 재처리 큐 등록/해제 | 4-5 데이터 오류 대응 |

> 마스터 계정 최초 생성은 시스템 시드 계정(배포 시 1개 생성) 방식으로 시작하고, 이후 마스터가 추가 마스터를 지정하는 절차는 P1로 후순위.

### 7-3. 신뢰도·그라운딩 UX 명세

이 서비스의 핵심 차별점(1-5 KPI: 환각률/근거일치율)이 실제로 화면에 드러나야 하는 부분.

| 요소 | 규칙 |
|---|---|
| 출처 인용 | 답변 문장 옆에 각주형 배지(예: `[1]`) → 클릭 시 원문 조문/회의록/예산 항목으로 스크롤 이동 또는 팝오버 미리보기 |
| 신뢰도 배지 | 답변 상단에 **높음/보통/낮음** 3단계 배지. "낮음"은 경고 색상 + "근거가 제한적입니다" 문구 |
| 답변불가 화면 | 검색 결과가 있지만 근거가 불충분할 때, 빈 결과와 **구분되는** 별도 상태: "관련 자료는 있으나 충분한 근거를 찾지 못해 답변을 제공하지 않습니다" + 관련 원문 링크만 제공 |
| 엄격/유연 적용 차등 | ①③(법령·조례)은 신뢰도 "낮음" 시 답변 자체를 답변불가로 강제 전환. ⑥(보고서)은 낮음 배지만 표시하고 답변은 제공(사람이 검토하는 영역이므로) |

> 3-3 상태별 화면 설계의 "결과 없음/오류"와는 별개로, "근거부족(답변불가)"을 검색형 화면 공통 상태로 추가해야 함.

| 7-3 | 신뢰도·그라운딩 UX | **P0** | 서비스 핵심 차별점, 없으면 오답을 사실처럼 노출하는 리스크 |
| 7-4 | 온보딩 | P1 | 없어도 서비스는 돌아가나, ⑥ 품질 리스크 완화에 필요 |
| 7-5 | 피드백 루프 | **P0** | KPI(환각률/채택률) 자체가 이 데이터 없이는 측정 불가 |
| 7-6 | 검색 필터/비교표 UI | P1 | MVP는 필터 없이도 기능함, UX 품질 문제 |
| 7-7 | 알림센터 | P2 | 대시보드 카드만으로 초기 운영 가능 |
| 7-8 | 예산 시각화 고도화 | P2 | 증감표만으로 MVP 기능은 충족 |
| 7-9 | 보고서 편집/내보내기 | P1 | 초안 확인만으론 실사용에 부족(내보내기는 실사용 필수에 가까움) |
| 7-10 | 대화 이력 관리 세부 | P2 | 목록 조회만으로 최소 기능 충족 |
| 7-11 | 에러·엣지케이스 | **P0** | 4-5 안정성 대비가 화면으로 안 내려가면 오류 시 사용자가 멈춤 |
| 7-12 | 보안·감사로그 | P1 | 민감정보 특성상 오픈 전 필요하나 개발 순서상 후반 배치 가능 |

> 6장의 구현 순서(①③→②⑤→④→⑥)에 **P0 항목(7-1, 7-2 승인 대기열, 7-3, 7-5, 7-11)을 각 기능 구현과 동시에 병행**하는 것을 권장. 화면 기능만 만들고 로그인·신뢰도 UX·에러 처리를 나중에 붙이면 재작업 비용이 커짐.

## 8. UI 의사결정 (v1.1) — 프레임 목업 검수 확정

> 7장 스펙을 전 화면(21개 라우트) 실동작 프레임 목업으로 구현·검수한 뒤 확정한 사항. "결정했다"는 화면 동작·패턴이 코드로 검증됐다는 뜻이며, 색상(테마)은 다음 단계에서 별도로 다룸.

### 8-1. 컴포넌트 스택 확정

| 항목 | 결정 | 비고 |
|---|---|---|
| shadcn CLI 프리셋 | **Nova** + `-b radix` (Base UI 아님) | 최신 CLI가 style/baseColor 프롬프트를 preset 방식으로 개편하면서 5-4의 "Slate + New York" 명칭이 사라짐. Base UI로 초기화되면 `asChild`가 깨져 Radix로 재초기화 |
| 색상 베이스 | Slate 느낌 유지 | CLI에 Slate 프리셋이 없어 클래식 shadcn Slate HSL 값을 `globals.css`에 수동 이식 |
| Border radius | `0.5rem` | New York 스타일 특유의 각지고 담백한 느낌 재현 |
| 폰트 | `Pretendard`(본문) + `Geist Mono`(숫자/코드) | 기본 Geist는 한글 글리프 미포함. 최초엔 `Noto Sans KR`로 임시 대응 후, 가독성이 더 좋은 `Pretendard`로 교체(변수 폰트, `next/font/local`로 자체 호스팅) |
| 차트 | `recharts` + shadcn `chart` 래퍼 | 예산 화면의 부서별 비교 막대그래프 |

### 8-2. 네비게이션·접근 정책 확정

| 항목 | 결정 |
|---|---|
| 사이드바 구조 | 업무 5메뉴(그룹1) + 관리자 콘솔 4메뉴(그룹2, "관리자 전용" 라벨) + 마이페이지(하단, 서브메뉴 3개) |
| 관리자 콘솔 노출 | 목업 단계는 항상 노출(검수 편의). **실제 인증 연동 시 마스터 권한 계정에만 조건부 렌더링**(7-2 원칙 유지) — 프론트 라우트 가드는 인증 붙는 시점에 별도 구현 필요 |
| 모바일 대응 | 사이드바는 오프캔버스 Sheet로 자동 전환(shadcn 내장), 대화 목록도 `md` 미만에서 Sheet 전환 |

### 8-3. 대화(채팅) 인터랙션 확정

| 항목 | 결정 |
|---|---|
| 전송 플로우 | 사용자 발화 즉시 반영 → 로딩 스켈레톤 → 목업 답변 도착 (실제 RAG 연결 시 이 구간이 API 호출로 대체) |
| 새 대화 | 목록 최상단에 즉시 생성 + 빈 스레드로 전환 |
| 이름 변경 | 목록 행 내 인라인 편집(Enter 저장/Esc 취소) |
| 삭제 | AlertDialog 확인 후 삭제, 활성 대화 삭제 시 다음 항목으로 자동 전환 |
| 검색 | 대화 목록 상단 검색창, 클라이언트 사이드 제목 필터 |

### 8-4. 상태 표현 확정

| 상태 | 표현 방식 |
|---|---|
| 신뢰도 높음/보통/낮음 | 초록/노랑/빨강 배지, "낮음"은 경고 문구 동반 |
| 답변불가(근거부족) | 점선 테두리 + 주황 톤, "결과없음"과 시각적으로 구분 |
| 결과없음 | 점선 테두리 + 중립 톤 + 재탐색 유도 문구 |
| 오류 | 점선 테두리 + 빨강 톤 + "다시 시도" 버튼(클릭 시 로딩 후 복구) |
| 데이터 신뢰도(최신 반영일) | 헤더 상단 배지, 정상/지연/오류 3단계 (클릭 시 상태 예시 순환 — 실제로는 배치 상태에 따라 자동 결정) |

### 8-5. 알림·세션 확정

| 항목 | 결정 |

| 알림센터 | 헤더 드롭다운 미리보기(클릭 시 읽음 처리) + `/notifications` 전체 목록(유형 필터: 안건/보고서/조례/데이터) + 클릭 시 관련 화면으로 이동 |

`접수됨 → 생성중 → 초안생성됨 → 검토중 → 완료/보류` 5단계가 버튼 클릭으로 실제 전이되도록 확정.

## 9. 테마 확정 (v1.1) — 그린 + 테라코타

> 5-3에서 정한 방향(따뜻한 뉴트럴 + 그린·테라코타 포인트)을 구체적인 색상값으로 확정. 결정 과정은 인터뷰(톤/포인트 강도/신뢰감 vs 친근함/다크모드 우선순위) 방식으로 진행.

### 9-1. 인터뷰 결과

| 질문 | 결정 |
|---|---|
| 그린 톤 | **포레스트 그린**(짙은 초록) — 세이지·올리브·에메랄드 대비 신뢰감·안정감이 가장 강함 |
| 테라코타 포인트 강도 | **은은하게** — 배지·hover 등 작은 강조 요소에만 사용, 주요 버튼(CTA)은 그린 유지 |
| 톤 밸런스 | **신뢰감 우선** — 채도를 낮추고 차분하게. 5-3의 "친근함"은 배경의 따뜻한 뉴트럴 톤으로만 은은히 표현 |
| 다크모드 우선순위 | **라이트모드 중심** — 다크모드는 기본 대응 수준(정교한 별도 튜닝 없음) |

### 9-2. 확정 색상 토큰 (라이트모드)

| 토큰 | 값(HSL) | 컴파일 결과 | 용도 |
|---|---|---|---|
| `--background` | `hsl(30 20% 99%)` | `#fdfcfc` | 전체 배경 (기존 Slate의 푸른기 제거, 따뜻한 뉴트럴로 교체) |
| `--foreground` | `hsl(140 10% 14%)` | — | 기본 텍스트 (아주 옅은 그린 언더톤) |
| `--primary` | `hsl(155 25% 24%)` | `#2e4c40` | 버튼·링크·포커스링 등 브랜드 그린 |
| `--accent` / `--sidebar-accent` | `hsl(16 45% 93%)` / `hsl(16 40% 91%)` | `#f5e9e5` / `#f1e4df` | 테라코타 — 드롭다운·셀렉트·사이드바 hover/active 전용(컴포넌트 스캔으로 사용처 확인 후 이 범위로 한정) |
| `--chart-1~5` | 그린 단일 톤 램프(연한→짙은) | — | 예산 화면 등 데이터 시각화. 테라코타는 데이터 색상에 사용하지 않음("은은하게" 원칙 유지) |
| `--destructive` | `hsl(4 72% 51%)` | — | 경고/삭제, 기존 붉은 계열 유지 |

> 신뢰도 배지(높음/보통/낮음)와 상태 배지(성공/경고/오류)는 브랜드 컬러와 분리된 시맨틱 컬러(emerald/amber/red)를 그대로 사용 — 테마 교체와 무관하게 의미가 고정되어야 하므로 별도 유지.

### 9-3. 다크모드

라이트모드 팔레트를 기준으로 배경/카드/보더만 따뜻한 다크 뉴트럴로, 그린은 대비 확보를 위해 밝기를 올린 세이지 톤(`#6aaf8c`)으로 조정. 테라코타 accent도 다크 배경에 맞게 반전(어두운 배경 + 밝은 텍스트)만 적용하고 별도 미세조정은 하지 않음(9-1 결정에 따름).

### 9-4. 적용 범위

`src/app/globals.css`의 `:root`/`.dark` 토큰만 교체 — 컴포넌트 구조·레이아웃은 8장에서 확정한 그대로 유지(5-4에서 계획한 "구조와 색상 분리" 원칙대로 진행됨). 전체 21개 라우트 재검증 완료, 컴파일·타입체크·lint 이상 없음.
